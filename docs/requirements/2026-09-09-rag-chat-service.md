## Goal

基于已沉淀的云端知识库（`summary_segment` + pgvector 向量检索），提供穿搭问答服务：

- **场景一（照片输入）**：用户上传当前穿搭照片 → 服务端压缩后存 COS → 多模态模型产出"用户穿搭描述" → 以描述为 query 向量检索 → 生成针对性优化建议。
- **场景二（文本输入）**：用户文字描述穿搭期望 → 向量检索 → 生成实现路径。
- 支持单用户多轮追问（query 重写 + 会话历史上下文）。
- 回答为**三段式引用结构**（正文 + 图片示例 + 视频注脚），严格"无命中不编造"兜底。
- 提供同仓库独立路由页的聊天前端。

## 决策（已确认）

1. **双场景一期同时交付**（用户 2026-09-09 确认）。
2. **前端形态：同仓库独立路由页**（用户 2026-09-09 确认）：现有 React SPA 内新增独立路由/入口，非独立包、非独立仓库（与讨论假设一致）。
3. **非流式 JSON 回答**（用户 2026-09-09 确认）：一次性返回三段式回答对象，不做 SSE/打字机。
4. 继承讨论稿已确认决策：多模态大模型做照片分析与聊天生成；**视觉输入默认开启、配置开关可关闭**；兜底严格"暂无相关内容"，不附带通用穿搭常识；会话存 PostgreSQL（与知识库同库）；照片先压缩一次再存 COS（公开读，隐私策略后置）；照片不进入知识库；起步无鉴权。
5. 追加确认（2026-09-09，用户）：旧会话支持主动删除（二次确认，级联删消息，COS 照片文件靠专属目录后续清理）；用户上传照片统一存 COS 专属固定前缀目录（便于后续批量清理）；**照片分析与聊天生成均使用当前用户配置的模型**（不新增模型配置项）。

## In Scope

### 后端（`packages/server/`）

- **会话数据模型**：新增 `conversation` / `message` 表（结构见讨论稿草案；`message` 含 `role`、`content`、`photo_urls TEXT[]`、`reply_images JSONB`、`reply_sources JSONB`）。schema 经 Prisma contract/migration 管理（`migration plan` + `db migrate`），不手写 DDL。
- **照片上传 API**：`POST /api/chat/photos`（multipart）：服务端压缩一次（参数见 Open Questions 默认值）→ 存 COS `user-photos/<conversationId>/...` → 返回公网 URL。多张按多次调用或一次多文件，plan 定。
- **会话 API**：
  - `POST /api/chat/conversations`：创建会话；
  - `GET /api/chat/conversations`：会话列表；
  - `GET /api/chat/conversations/:id/messages`：历史消息（含三段式回答）；
  - `POST /api/chat/conversations/:id/messages`：发送问题（body 携带文本与可选 `photoUrls`），同步返回本轮回答（非流式）；
  - `DELETE /api/chat/conversations/:id`：删除会话（级联删 messages，见 Business Rules）。
- **每轮处理管道**（server 内服务编排，复用 Phase 2 检索的 service 层能力而非自调 HTTP）：
  1. **query 重写**：多轮场景下 LLM 基于会话历史把省略式追问补全为可独立检索的问题（首轮直接使用原文）；
  2. **照片分析**（仅本轮携带照片时）：多模态模型分析照片 → 结构化"用户穿搭描述"（体型/单品/颜色/风格/可优化点），作为检索 query 的一部分；photo URL 走 vision proxy 的 URL 透传形态；
  3. **向量检索**：归一化 query → embedding → pgvector top-k（k 默认 10，沿用 Phase 2 归一化与 `embedding_model` 一致性过滤）；
  4. **回答生成**：多模态模型，输入 = 文本上下文（命中技巧 title/content + 最近 N 轮历史）+ 视觉输入（默认开启：命中技巧截图 COS URL；场景相关轮次含用户照片）→ 输出正文 + `[n]` 引用标记；
  5. **三段式拼装**：服务端解析 `[n]` 标记，组装 `{ text, images, sources }` 回答对象（结构同讨论稿），`sources` 含 `videoTitle/videoUrl/timestampSeconds` 供 B 站 `?t=` 跳转。
- **系统提示词**：只基于给定技巧回答（按"是什么/为什么/怎么穿"组织）、综合多条命中技巧、不编造知识库外方法、`[n]` 标注引用、无命中/低置信度时明确回答"知识库暂无相关内容"。
- **配置**：视觉输入开关、检索命中阈值、历史轮数 N 等以环境变量/配置项提供；模型使用当前用户配置的模型（不新增模型配置项）（命名与默认值 plan 定）；`.env.example` / compose 补充说明。
- **vision proxy 增强（最小范围）**：按需评估——模型名已由 Node 传入（无需改）；若问答模型走标准 DashScope 端点则基址需配置化（当前硬编码内网 MaaS 端点）。**非流式已确认，无需流式透传**。具体范围 plan 评估后定，保持 HTTP 契约耦合。

### 前端（`packages/frontend/`）

- 新增独立路由页（聊天界面）：会话列表（全部保留会话，按最近更新倒序，支持删除会话）/新建会话、点击旧会话回看历史并继续发送、消息流、照片上传（多选）、三段式回答渲染（正文含 `[n]` 标记解析、图片示例区、底部视频注脚含 B 站 `?t=` 跳转链接）、加载/失败/空态。
- 复用现有技术栈（Zustand + antd + TanStack Query），不引入新框架。

## Out Of Scope

- SSE 流式输出。
- 用户穿搭照片的体型/风格元数据过滤检索（讨论稿标注"后期可选"）。
- BM25 / 混合检索 / 检索评估集建设（数据量增长后评估）。
- 会话保留时长限制与清理任务（暂不限制，运营后定）。
- embedding 模型/维度变更重算工具（Phase 4）、删除/重总结对 COS 文件的级联治理（Phase 4）。
- 现有主应用 UI 的改动（问答入口链接除外）。

## Main User Flows

### 场景二：文本问答

1. 用户在问答页新建会话，输入"小个子怎么穿显高"。
2. 服务端检索（纯向量 top-k）→ 命中多条技巧 → 生成带 `[n]` 引用的建议正文。
3. 前端渲染：正文 + 命中技巧截图（images 区）+ 视频注脚（sources 区，可跳转原视频对应时刻）。

### 场景一：照片问答

1. 用户在会话中上传穿搭照片 + 可选文字（"我穿这样，怎么改进？"）。
2. 照片上传接口压缩后存 COS → 消息发送携带 photoUrl → 多模态模型产出穿搭描述 → 描述 + 文字检索 → 生成针对性建议。
3. 渲染同上。

### 多轮追问

1. 上一轮问答后，用户追问"那配什么鞋子？"。
2. 服务端基于历史 query 重写 → 检索 → 生成（携带最近 N 轮历史）。
3. 历史轮次的回答可回看（含图片与视频注脚）。

### 旧会话回看与继续

1. 用户打开新的会话继续问新话题；旧会话完整保留，不因新建而受影响。
2. 用户从会话列表点击任意旧会话 → 回看全部历史消息（含三段式回答）→ 直接在消息框继续发送新问题。
3. 服务端基于该旧会话的既有历史做 query 重写与生成，上下文与中断前连续（如旧会话聊过"小个子显高"，重开后问"那鞋子呢"仍能衔接）。
4. 旧会话中的历史照片继续可用（COS URL 持久存储）。

### 兜底

检索无命中或低于阈值 → 回答固定兜底文案"知识库暂无相关内容"，无 images/sources。

## Business Rules

- 严格兜底：无命中/低置信度不编造、不附带通用穿搭常识；是否命中由"top-k 结果 + 命中阈值"判定（阈值配置项，默认值 plan 定）。
- 一轮消息 = 一条 user message + 一条 assistant message；assistant message 持久化三段式回答（`reply_images`/`reply_sources` JSONB）与正文。
- 会话内照片仅服务当前会话（分析上下文 + 生成视觉输入），不写入知识库、不参与向量检索库。
- 照片上传即压缩一次；压缩后 URL 存入 `message.photo_urls`，后续轮次复用 URL（不重复上传）。
- 视觉输入开关关闭时：生成退化为纯文本，截图/照片仅在前端展示（检索与流程不变）。
- 检索沿用 Phase 2 业务规则：`embedding_model` 与当前配置一致的 segment 才参与匹配；归一化同款。
- **会话保留**：所有会话持久保留、不自动清理、不设过期（Phase 3 无保留时长限制，运营后视情况定）；新建会话不影响任何旧会话。
- **旧会话可继续**：任意旧会话可随时打开回看并继续发送消息；继续讨论时 query 重写与生成上下文基于该会话历史（受最近 N 轮窗口限制），与会话内先后顺序无关。
- **旧会话可删除**：仅用户主动删除时删除会话（级联删 messages，DB 行为）；删除为不可恢复操作，前端需二次确认；COS 上已传照片文件随删除不主动清理（统一依赖专属目录的后续批量清理，见下条与 Phase 4）。
- **用户照片专属目录**：所有用户上传照片统一存 COS 专属固定前缀目录下（如 `user-photos/`，会话子结构由 plan 定，但根前缀必须专属且固定，不与其他用途混用），便于后续按前缀整目录批量清理。

## Roles / Permissions

- 单用户工具，无角色/权限系统；问答 API 无鉴权（与现有 `/api/*` 一致）。
- DashScope API Key 沿用现有密钥管理（不入日志、不进镜像、不进 git）。
- 注意：若未来公开运营需引入鉴权/限流，属保护区域，需重新走需求 + owner doc 流程。

## Edge Cases

- `content` 为空且无照片的消息：400。
- 照片格式不支持 / 超过大小上限：400（上限值 plan 定）。
- 照片上传 COS 失败：返回明确错误，消息不落库（发送终止）。
- 照片分析失败（vision proxy / 多模态调用失败）：返回错误并提示重试；不降级为纯文本静默回答。
- 检索命中但生成失败：user message 已落库、assistant message 记录失败态（或本轮不落 assistant，plan 定），前端可重试。
- 缺 LLM/embedding 配置：发送时返回 503 语义错误（同 Phase 2 检索缺配置语义）。
- `conversationId` 不存在：404。
- 会话历史过长：仅携带最近 N 轮作为生成上下文（N 配置项）。
- 旧会话中的历史照片 URL 失效（COS 文件被外部删除）：前端对该图降级展示（占位/隐藏），不影响文本历史与继续讨论；不在本期做 URL 有效性校验。
- 删除会话与该会话生成中并发：以删除为准，删除后生成结果不再落库；前端提示（并发细节 plan 定）。
- 删除已不存在的会话：404（幂等语义由 plan 定）。
- 知识库为空 / 全部未向量化：恒走兜底文案。
- 会话标题：首条消息截断生成（前端展示用，plan 细化）。
