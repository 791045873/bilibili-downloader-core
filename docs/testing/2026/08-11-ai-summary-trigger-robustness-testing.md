# 2026-08-11 AI 总结触发健壮性 — 测试方向

关联计划：`docs/plans/2026-08-11-ai-summary-trigger-robustness-plan.md`

本文件描述触发链路健壮性应观察到的需求级状态与反状态，供计划验证与闭核算使用。验证命令：`pnpm typecheck`（零错误）+ 下述手工回归。

## 1. trigger 全量错误落地 failed

**应成立:**

- `trigger()` 中任意阶段（前置决策、目录准备、低清调度、LLM 配置）异常时，任务 `summaryStatus` 与资源级 `ai_summary_task` 都落 `failed`，并带明确错误信息。
- 失败时发出失败通知（如 SMTP 已配置）。

**不应成立:**

- 任何入口（任务页按钮、一键总结、自动触发）出现"显示触发中/返回成功，但状态永久卡 `pending` 且无错误"的静默失败。

## 2. 资源级与任务级入口守卫一致

**应成立:**

- `POST /api/analysis/trigger` 与 `POST /api/tasks/:id/summary` 对"同一资源 AI 总结进行中"都返回冲突（409/400 语义），拒绝重复触发。
- 首次触发不受影响。

**不应成立:**

- 资源级入口在总结进行中仍可重复触发（现有不一致）。

## 3. 并发双点触发不双跑

**应成立:**

- 同一资源被快速连续触发两次时，只认领一次（DB 条件更新认领原语生效），第二次被拒绝；不出现两个并发分析任务。
- 低清下载去重正确，不重复调度同一低清子任务。

**不应成立:**

- 并发双点导致同一资源双跑分析或双份低清下载。

## 4. 启动对账恢复（Phase 2）

**应成立:**

- 服务重启后，遗留 `analysis_sub_task`（created/downloading）被标记 `failed` 并带"服务重启"错误信息。
- `summaryStatus` 为 pending/analyzing 且无进行中子任务的任务落 `failed`，UI 不再永久显示"总结中/待总结"。
- 用户手动重触发可顺畅新建子任务、重新下载低清并继续。

**不应成立:**

- 重启后出现永久 `pending`/`analyzing` 卡死；重触发继续等待一个永远不会完成的子任务。

## 5. 启动不自动重触发（保守决策）

**应成立:**

- 服务启动时不自动发起分析或下载（仅对账标记 failed），避免开机即产生意外网络流量。

**不应成立:**

- 启动时自动重触发大量分析/下载。

## 6. 既有行为不回归

**应成立:**

- 正常自动总结、任务级/资源级触发、低清下载完成后自动续跑的行为不变。

**不应成立:**

- 守卫统一或认领原语导致正常单次触发被误拒。

## 手工回归清单

- 场景 A：正常触发 → 分析 → 成功（基线）。
- 场景 B：构造前置错误（如删除 QWEN 配置导致 `getLlmConfig` 抛错）→ 任务落 failed 且带错误，UI 可见。
- 场景 C：总结进行中重复触发 → 返回冲突。
- 场景 D：并发快速双点 → 只认领一次。
- 场景 E：重启后子任务 created → failed；重触发恢复（Phase 2）。
- 场景 F：`pnpm typecheck` 零错误。

运行级场景（B/C/D/E）需要运行中的 server、真实下载链路或真实进程重启，无法在静态验证中复现；逻辑级已通过代码检查覆盖（认领原语 SQL 互斥、try/catch 落 failed 分支、对账 SQL），运行级行为留用户手动验证。`pnpm typecheck`、`pnpm build` 已在实施时通过。

范围外：磁盘校验与缺失重下（资源可用性计划）、状态单一来源与子任务资源键（架构收敛计划）。
